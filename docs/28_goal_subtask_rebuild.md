# 目標サブタスク再設計

最終更新: 2026-07-29

## 1. 文書の目的

現在の目標サブタスク機能を安全に取り除き、新しい仕様へ置き換えるための調査、仕様、移行、実装方針を管理する。

この文書では、現行機能を調査した事実と、今後決定する新仕様を分けて記録する。新仕様と移行方針が確定するまで、既存のDBテーブル、リレーション、API、データは削除しない。

上位方針は次の文書に従う。

- `docs/01_overall_policy.md`
- `docs/27_mobile_first_feature_reorganization.md`

## 2. 進行工程

1. 現行サブタスク機能を棚卸しする。
2. 新サブタスク仕様を整理、確定する。
3. 現行実装と新仕様の差分表を作成する。
4. DB構造の流用可否を判断する。
5. 既存データの維持、変換、削除方針を決定する。
6. 新実装へ段階的に置き換える。
7. 他機能への影響を確認し、検証する。

## 3. 工程1: 現行機能の棚卸し

状態: 完了

### 3.1 現行仕様

`docs/27_mobile_first_feature_reorganization.md`では、次の内容が確定事項として記載されている。

- 通常目標の詳細でサブタスクを扱う。
- 目標詳細モーダルは「概要・関連情報」と「サブタスク」のタブ構成とする。
- サブタスクがない場合、空の内容を常時表示しない。
- サブタスクタブは1件以上ある場合だけ表示する。
- 0件の目標へ追加する場合は専用編集画面を使用する。
- 詳細モーダルから作成者だけが専用編集画面へ移動できる。
- 個人目標とサブタスクへ役割を集約し、旧個人タスク機能は削除する。
- 個人目標は所有者以外へ存在自体を返さない。
- 団内目標は認証済み利用者が閲覧できる。
- サブタスクを追加、編集、削除できるのは目標の作成者だけとする。

現行仕様には、次の内容が定義されていない。

- サブタスクの具体的な利用目的
- 対象にできる目標の種類
- 作成、名称変更、削除、完了切り替えを行う各画面
- 完了済みサブタスクの表示方法
- 並べ替え操作
- 最大件数
- タイトルの最大文字数
- 親目標の完了、削除との関係
- サブタスクの一括操作
- 新旧データの移行方針

### 3.2 現行画面

#### ホームの目標詳細モーダル

実装: `src/pages/HomePage.tsx`

- 通常目標のカードから詳細モーダルを開く。
- 「概要・関連情報」と「サブタスク」のタブを常に表示する。
- サブタスクを`sortOrder`、作成日時の順で表示する。
- 目標の作成者はチェックボックスで完了、未完了を切り替えられる。
- 作成者以外のチェックボックスは無効になる。
- 目標の作成者は詳細モーダル内の入力欄からサブタスクを追加できる。
- 名称変更、削除、並べ替えのUIはない。
- 追加または完了切り替え後は目標一覧全体を再取得する。
- 更新失敗時のエラー表示はある。
- 完了切り替え中の無効化、項目単位のローディング、連打防止はない。

サブタスクが0件でもタブと追加欄を表示するため、現行仕様書の「1件以上の場合だけタブを表示」「0件からの追加は専用編集画面」と一致していない。

#### 目標編集画面

実装: `src/pages/GoalEditorPage.tsx`

- タイトル、概要、メモだけを編集できる。
- サブタスクの表示、追加、名称変更、削除、並べ替えはできない。

このため、現行仕様書が指定する「0件から専用編集画面で追加」は実装されていない。

#### 目標作成画面

実装: `src/pages/HomePage.tsx`

- 新規目標ではタイトルと概要だけを入力する。
- 目標作成と同時にサブタスクを登録することはできない。

### 3.3 フロントエンドAPI契約

実装: `src/lib/api.ts`

`Goal`レスポンスには常に`subTasks: GoalSubTask[]`が含まれる。

`GoalSubTask`は次の項目を持つ。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `id` | `string` | サブタスクID |
| `goalId` | `string` | 親目標ID |
| `title` | `string` | タイトル |
| `isDone` | `boolean` | 完了状態 |
| `sortOrder` | `number` | 表示順 |
| `createdAt` | `string` | 作成日時 |
| `updatedAt` | `string` | 更新日時 |

公開されている呼び出しは次の3つである。

- `createGoalSubTask`: 新規作成
- `updateGoalSubTaskNew`: タイトルまたは完了状態の更新
- `deleteGoalSubTaskNew`: 削除

`updateGoalSubTaskNew`と`deleteGoalSubTaskNew`は現在の画面から呼び出されていない部分を含む。完了状態の更新だけが使用され、タイトル更新と削除は未使用である。

### 3.4 サーバーAPI

実装: `server/routes/goals.ts`

すべての目標APIには`requireAuth`が適用される。

#### 目標取得

- `GET /api/goals`
- `GET /api/goals/:id`

目標取得時は、サブタスクを`sortOrder`昇順、作成日時昇順で含める。

個人目標の一覧は本人のデータだけを返す。目標詳細は、本人の目標または団内目標だけを返す。このため、個人目標に属するサブタスクも所有者以外へ返らない。

#### サブタスク作成

- `POST /api/goals/:id/sub-tasks`

親目標を`id`と現在のユーザーの`ownerId`で検索する。所有者でなければ作成できない。タイトルは前後の空白を除去し、空文字を拒否する。

作成時の`sortOrder`には、その目標に存在するサブタスク件数を設定する。同時作成時の重複や、削除後の並び順の欠番を補正する処理はない。

#### サブタスク更新

- `PATCH /api/goals/:id/sub-tasks/:subTaskId`

サブタスクID、親目標ID、親目標の所有者を同時に確認する。タイトルと完了状態を更新できる。

タイトルが空文字の場合はエラーにせず、既存タイトルを維持する。タイトルの最大文字数は検証していない。

#### サブタスク削除

- `DELETE /api/goals/:id/sub-tasks/:subTaskId`

サブタスクID、親目標ID、親目標の所有者を同時に確認する。削除後に残った項目の`sortOrder`は詰め直さない。

### 3.5 DB構造

実装: `prisma/schema.prisma`

`Goal`と`GoalSubTask`は1対多の関係である。

```text
Goal 1 ── 0..n GoalSubTask
```

`GoalSubTask`は次の列を持つ。

| 列 | 制約・初期値 |
| --- | --- |
| `id` | 主キー、CUID |
| `goalId` | 必須、`Goal.id`への外部キー |
| `title` | 必須 |
| `isDone` | 必須、初期値`false` |
| `sortOrder` | 必須、初期値`0` |
| `createdAt` | 必須、作成時刻 |
| `updatedAt` | 必須、自動更新 |

`goalId`には単独インデックスがある。親目標を削除すると、外部キーの`ON DELETE CASCADE`によって所属するサブタスクも削除される。

タイトル長、目標ごとの最大件数、`sortOrder`の一意性を保証するDB制約はない。

### 3.6 migration履歴

`prisma/migrations/20260603234000_add_goal_links_and_tasks`で`goal_sub_tasks`テーブルが作成された。当初は旧`shared_goals`テーブルを参照していた。

`prisma/migrations/20260725090000_mobile_first_reorganization`では次の処理が行われる。

- 廃止状態に属する旧目標のサブタスクを削除する。
- 維持対象の旧目標を新しい`goals`テーブルへ移す。
- `goal_sub_tasks`テーブル自体と維持対象のデータは残す。
- 外部キーを新しい`goals`テーブルへ付け替える。

このmigrationはまだ本番DBへ適用していないと`HANDOFF.md`に記載されている。新仕様のDB移行を設計するときは、本番環境とローカル想定で参照先テーブルの状態が異なる可能性を考慮する必要がある。

### 3.7 他機能との依存関係

サブタスクは次の処理と直接または間接に結び付いている。

- 個人目標一覧
- 団内目標一覧
- 通常目標詳細
- 目標編集への遷移
- 目標本体の削除
- 周回目標の連携カード削除
- 進捗管理の連携カード削除
- 旧個人タスク機能を削除した後の役割分担

周回目標と進捗管理の連携カードもDB上は`Goal`を使用するため、現在のAPIとDBはサブタスクを関連付けられる。ただし、現行UIでは連携カードから通常目標の詳細モーダルを開かないため、サブタスクを表示、操作する経路はない。

親目標の通常削除と連携解除は、どちらも最終的に`Goal`行を削除する。現在はCascadeによってサブタスクも同時に削除される。

### 3.9 既存データの確認状況

本工程ではDBへ接続せず、既存データを変更していない。そのため、環境ごとの次の値は未確認である。

- サブタスク総件数
- サブタスクを持つ目標数
- 個人目標と団内目標ごとの件数
- 完了、未完了ごとの件数
- 1目標あたりの最大件数
- `sortOrder`の重複または欠番
- タイトルの最大文字数
- 孤立行の有無

工程5までに、対象環境を確認したうえで読み取り専用のpreflight SQLを作成し、実行前にユーザー確認を取る。

### 3.10 現時点の安全判断

- 新仕様が確定するまで`GoalSubTask`モデルと`Goal.subTasks`リレーションを残す。
- `goal_sub_tasks`テーブルと既存データを削除しない。
- 既存APIを先に削除しない。
- 親目標削除時のCascadeを変更しない。
- 新UIへ切り替える前に現行UIだけを削除しない。
- 新仕様で同じ1対多関係と基本項目を使う場合は、既存構造の流用を第一候補とする。
- DB構造を置換する必要がある場合も、新構造への移行と利用箇所の切り替えを先に行い、旧構造の削除は別migrationに分ける。

## 4. 工程2: 新仕様の整理

状態: 完了

### 4.1 確定した要求

#### 目的

- 目標画面で作成した目標を達成するために、必要な作業を細かく分けて管理する。
- 例えば「特定のクエストをクリアする」「特定の敵を討伐する」という目標に対して、武器の準備、素材収集、編成の組み立てなどをサブタスクとして管理する。

#### 作成と管理

- 目標の新規作成時にサブタスクを追加できる。
- 目標の作成後にもサブタスクを追加できる。
- 目標の作成後にサブタスクを削除できる。
- 親目標を削除した場合、その目標に付与されたサブタスクも同時に削除する。

#### 進捗表示

- 目標カードに、サブタスクの総数と達成済み件数を表示する。
- 総数7件、達成済み3件の場合は`3/7`と表示する。

#### サブタスクとして追加できるもの

- 通常のサブタスクを追加できる。
- 既存の周回目標をサブタスクとして設定できる。
- 既存の進捗目標をサブタスクとして設定できる。

### 4.2 用語の整理

新しいサブタスクは、次の3種類を持つ。

| 種類 | 内容 | 例 |
| --- | --- | --- |
| 通常サブタスク | 目標の中だけで管理するチェック項目 | 武器を作成する、編成を組む |
| 周回目標リンク | 既存の周回目標を参照する項目 | 素材を100個集める |
| 進捗目標リンク | 既存の進捗目標を参照する項目 | 武器を指定段階まで強化する |

数量目標と進捗目標は既存データそのものを複製せず、サブタスクから参照する。

#### G. 公開範囲と権限

34. 個人目標のサブタスクは、現在と同じく所有者だけが閲覧、操作できるか。

47. 通信失敗時に画面表示を元へ戻し、再操作できるようにするか。

### 4.4 既存機能との重複確認

通常目標には、サブタスク以外に`requiredItems`と`raidTargets`が存在する。

- `requiredItems`: 必要武器などの名称、必要数、現在数、重要度、メモ
- `raidTargets`: クエスト名、目標数、現在数、周回種別、メモ

新しいサブタスクで「必要な武器」「素材収集」「討伐」を扱う場合、これらの既存関連情報と役割が重複するため、次の事項を検討した。

48. `requiredItems`と`raidTargets`を今後も独立した関連情報として残すか。
49. 既存関連情報を新サブタスクへ統合するか。
50. 統合する場合、既存データを通常サブタスクまたは周回目標へ変換できるか。

- 目標新規作成時に複数のサブタスクを追加できる。

- 目標専用編集画面では、追加、タイトル変更、削除、並べ替えを行える。

#### カードの進捗

- 通常サブタスク、周回目標リンク、進捗目標リンクをすべて1件として数える。
- 達成済み件数と総件数を`3/7`形式で表示する。
- 0件の場合は進捗を表示しない。
- すべて達成した場合も、親目標を自動削除または自動完了しない。
- 親目標の完了、削除は利用者が手動で行う。

#### リンク項目の達成判定

- 周回目標リンクは、現在数が目標数以上になった場合に自動で達成済みとする。
- 進捗目標リンクは、その進捗目標に設定された最終目標まで進行した場合に自動で達成済みとする。
- 進捗目標の途中段階を、リンク項目独自の達成条件として指定する機能は設けない。

#### リンクと削除

- 同じ周回目標または進捗目標を、複数の通常目標から参照できる。
- 同じ通常目標内で、同じ参照元を重複登録できないようにする。
- 通常目標を削除した場合、通常サブタスクとリンク行を同時に削除する。
- 通常目標またはリンク項目を削除しても、参照元の周回目標、進捗目標は残す。
- 参照元の周回目標、進捗目標を削除した場合、対応するリンク行を自動削除する。

#### 公開範囲と権限

- 個人目標のサブタスクは、所有者だけが閲覧、操作できる。
- 団内目標のサブタスクは、団内全員が閲覧、操作できる。
- 団内目標では、目標作成者以外も通常サブタスクの追加、タイトル変更、完了切り替え、削除、並べ替えを行える。
- 個人の周回目標、進捗目標を団内目標へリンクできないようにする。
- 団内目標の共同操作では、同じデータを同時編集できないように制御する。

団内目標のサブタスクを全員が操作できる規則は、`docs/27_mobile_first_feature_reorganization.md`にある「サブタスクを追加、編集、削除できるのは作成者だけ」という現行規則を新仕様で置き換える。団内目標の内容とボード状態も団内全員が編集可能とし、親目標全体の削除だけを作成者に限定する。公開範囲を個人へ戻すことは禁止する。

### 4.10 保存、リンク操作、競合制御、旧データ

#### リンク項目の操作

- 数量目標リンクを選択した場合、現在数を更新するモーダルを開く。
- 進捗目標リンクを選択した場合、対象の進捗管理画面へ移動し、対象目標を開く。

サブタスク単体の完了切り替え、タイトル変更、削除、並べ替えにどの単位の更新日時を使用するかは、工程4のDB設計で決定する。

### 4.11 リンク解除、完了表示、一覧取得、旧関連情報

2026-07-29、次の内容を確定した。

- 数量目標リンクまたは進捗目標リンクを解除する前に確認を表示する。
- 完了した通常サブタスク、数量目標リンク、進捗目標リンクは、いずれも元の表示位置を維持する。
- 完了項目は背景色を変える。色だけに依存せず、アイコンや完了状態でも判別できるようにする。
- 数量目標リンクと進捗目標リンクは、目標詳細を取得した時点の最新状態から達成済みか判定する。
- 目標一覧APIは、各通常目標のサブタスク総数と達成済み件数を返す。
- 目標カードごとに追加のAPIリクエストを行わない。
- `requiredItems`と`raidTargets`の既存データは新仕様へ引き継がず削除する。
- `GoalRequiredItem`、`GoalRaidTarget`、関連テーブル、API型、目標取得処理、表示処理を最終的に廃止する。
- 実データとテーブルの削除は、工程5のpreflight確認後に新しいmigrationで実施する。

#### 一覧の達成数

目標一覧APIは、DB上の最新データを参照して各目標の集計結果を返す。

- 通常サブタスクは保存された`isDone`を使用する。
- 数量目標リンクは、参照元の`currentCount >= targetCount`で判定する。
- 進捗目標リンクは、最終ゴールまでに必要な通常段階がすべて完了しているかを既存の進捗計算と同じ規則で判定する。
- 3種類の達成数を合算し、`completedSubTaskCount`と`totalSubTaskCount`として返す。
- カードはこの集計値を使って`3/7`を表示する。
- 完了状態のコピーや定期同期用の値をサブタスク側へ保存せず、参照元の最新状態から算出する。これにより、数量目標または進捗目標を更新した直後に古い達成状態が残ることを防ぐ。

一覧取得時のDBクエリと進捗計算でN+1取得を発生させない具体的な実装は、工程4で設計する。

### 4.12 3種類の一覧とリンク項目の手動判定

#### 一覧

2026-07-29、次の内容を確定した。

- 通常サブタスク、数量目標リンク、進捗目標リンクは、同じサブタスク一覧へ混在して表示する。
- 種類別の固定グループには分けない。
- 3種類を共通の`sortOrder`で管理し、上下移動ボタンで自由に並べ替えられるようにする。
- 種類名の文字は常時表示せず、アイコンと色で区別する。
- 種類はアイコンと左端の線または枠の色、完了状態はカード全体の背景色で表現を分ける。
- アイコンには読み上げ用のラベルを付け、色だけに依存しない。

#### リンク項目の完了状態

2026-07-29、数量目標リンクと進捗目標リンクは、自動判定に加えて利用者が手動で完了状態を変更できる仕様として確定した。

単純な`isDone`では自動判定と手動操作のどちらを優先したか判別できないため、リンク項目には次の3状態を持たせる案を使用する。

| 手動判定 | 実際に表示する完了状態 |
| --- | --- |
| 自動 | 参照元から自動算出した結果 |
| 手動完了 | 自動算出結果にかかわらず完了 |
| 手動未完了 | 自動算出結果にかかわらず未完了 |

データ表現の基本方針:

```text
completionOverride = null       自動
completionOverride = true       手動完了
completionOverride = false      手動未完了
```

実際に表示する状態は次の規則で算出する。

```text
effectiveIsDone = completionOverride ?? automaticIsDone
```

手動判定を設定した後に参照元の数量または進捗が変わっても、手動判定を優先する。再び参照元と連動させるには「自動判定に戻す」操作で`completionOverride`を`null`へ戻す。

この方式により、例えば次の操作が可能になる。

- 数量が未達でも、ゲーム内で目的を満たしたと判断して手動完了にする。
- 数量が達成済みでも、追加作業が残っているため手動未完了にする。
- 手動判定を解除し、再び数量または進捗から自動判定する。

#### 手動判定のUI

- チェックボックスには`effectiveIsDone`を表示する。
- 自動判定中のチェックボックスを操作した場合は、操作後の状態を`completionOverride`へ保存する。
- 手動判定中は、手動操作であることを示すアイコンを表示する。
- 手動判定中だけ「自動判定に戻す」アイコンボタンを表示する。
- 「自動判定に戻す」を実行した場合は`completionOverride`を`null`へ戻し、最新の参照元から再判定する。
- アイコンボタンには`aria-label`と`title`を設定する。
- 目標カードの達成済み件数には`effectiveIsDone`を使用する。

### 4.13 団内公開時のリンク検証

2026-07-29、次の内容を確定した。

- 数量目標リンクまたは進捗目標リンクが1件でも付いている個人目標は、団内目標として公開できない。
- 通常サブタスクだけが付いている個人目標は団内公開できる。

- 一部だけ公開する、リンク項目だけ非表示にするなどの部分的な公開は行わない。

- 拒否時は「数量目標・進捗目標のリンクを解除してから公開してください」と表示する。

この検証により、個人所有の数量目標または進捗目標が、団内目標を通じて他ユーザーへ漏れることを防ぐ。

## 6. 工程4: DB構造の流用判断

状態: 完了

### 6.1 検討した構成

#### 案A: `GoalSubTask`を3種類で共用する

既存の`GoalSubTask`を順序付きの共通項目として維持し、種類と任意の参照先を追加する。

利点:

- 既存の`Goal`対`GoalSubTask`の1対多関係とCascadeを流用できる。
- 3種類を1つの`sortOrder`で並べやすい。
- 目標ごとの最大件数、取得、削除、並べ替えを共通処理にできる。
- 既存テーブルを削除して作り直す必要がない。

注意点:

- 種類によって使用する列が異なる。
- Prisma schemaだけでは「種類に応じてどの列を必須にするか」を完全に表現できない。
- API検証に加え、migrationでCHECK制約を追加する必要がある。

#### 案B: 種類ごとに別テーブルを作る

通常サブタスク、数量目標リンク、進捗目標リンクを別テーブルに保存する。

利点:

- 種類ごとの必須列をDB構造で明確に表せる。
- 使用しないnullable列を持たない。

注意点:

- 3種類共通の並び順を別の親テーブルまたは追加構造で管理する必要がある。
- 一覧取得、最大件数、並べ替え、削除、競合制御が複雑になる。
- 現在の`GoalSubTask`構造を流用する利点が小さくなる。

### 6.2 採用する構成

案Aを採用し、既存の`GoalSubTask`テーブルと`Goal.subTasks`リレーションを流用する。

想定するモデル構造:

```prisma
model GoalSubTask {
  id                     String        @id @default(cuid())
  goalId                 String
  kind                   String        @default("standard")
  title                  String?
  isDone                 Boolean       @default(false)
  sourceRoundGoalId      String?
  sourceProgressGoalId   String?
  completionOverride     Boolean?
  sortOrder              Int           @default(0)
  goal                   Goal          @relation(fields: [goalId], references: [id], onDelete: Cascade)
  sourceRoundGoal        RoundGoal?     @relation(fields: [sourceRoundGoalId], references: [id], onDelete: Cascade)
  sourceProgressGoal     ProgressGoal?  @relation(fields: [sourceProgressGoalId], references: [id], onDelete: Cascade)
  createdAt              DateTime       @default(now())
  updatedAt              DateTime       @updatedAt

  @@unique([goalId, sourceRoundGoalId])
  @@unique([goalId, sourceProgressGoalId])
  @@index([goalId, sortOrder])
  @@index([sourceRoundGoalId])
  @@index([sourceProgressGoalId])
  @@map("goal_sub_tasks")
}
```

実際のフィールド名とmigration名は実装時に既存命名規則へ合わせる。

### 6.3 種類ごとの列

内部値には既存の`RoundGoal`との対応が分かる名称を使用する。

| `kind` | `title` | `isDone` | 数量目標参照 | 進捗目標参照 | `completionOverride` |
| --- | --- | --- | --- | --- | --- |
| `standard` | 必須 | 使用 | なし | なし | なし |
| `round` | なし | 使用しない | 必須 | なし | 任意 |
| `progress` | なし | 使用しない | なし | 必須 | 任意 |

リンク項目のタイトルは複製せず、参照元の最新タイトルを表示する。これにより、数量目標または進捗目標の名称変更がサブタスクへ自動反映される。

`isDone`は通常サブタスクだけに使用する。リンク項目の実効完了状態は、`completionOverride`と参照元から算出する。

### 6.4 DB制約

migrationで、少なくとも次の整合性を保証する。

- `kind`は`standard`、`round`、`progress`のいずれか。
- `standard`は空でない`title`を持ち、参照先と`completionOverride`を持たない。
- `round`は`sourceRoundGoalId`だけを持ち、`title`と`sourceProgressGoalId`を持たない。
- `progress`は`sourceProgressGoalId`だけを持ち、`title`と`sourceRoundGoalId`を持たない。
- 同じ親目標内で同じ数量目標を重複参照できない。
- 同じ親目標内で同じ進捗目標を重複参照できない。
- 親目標を削除すると3種類すべてを削除する。
- 参照元を削除すると対応するリンク項目だけを削除する。

タイトル100文字と最大50件は、PostgreSQLの文字列型や行単位CHECKだけでは目標単位の要件を十分に扱えないため、APIで検証する。タイトルについてはDBのCHECK制約でも文字数を補強する。

### 6.5 参照とCascade

| 削除操作 | DBの結果 |
| --- | --- |
| 通常目標を削除 | 所属する3種類のサブタスクをCascade削除 |
| 通常サブタスクを削除 | その行だけ削除 |
| 数量目標リンクを解除 | リンク行だけ削除し、数量目標は維持 |
| 進捗目標リンクを解除 | リンク行だけ削除し、進捗目標は維持 |
| 参照元の数量目標を削除 | 対応するすべてのリンク行をCascade削除 |
| 参照元の進捗目標を削除 | 対応するすべてのリンク行をCascade削除 |

### 6.6 競合検出の単位

競合範囲を不必要に広げず、同じデータの上書きを防ぐため次の単位を使用する。

- 目標のタイトル、概要、メモ、ボード状態: `Goal.updatedAt`
- 通常サブタスクのタイトル、完了状態: `GoalSubTask.updatedAt`
- リンク項目の手動判定: `GoalSubTask.updatedAt`
- サブタスクの追加、削除、並べ替え: 親の`Goal.updatedAt`

Prismaでは子行の変更だけでは親の`Goal.updatedAt`が自動更新されないため、追加、削除、並べ替えのトランザクション内で親目標の`updatedAt`を明示的に更新する。

サブタスク単体の完了切り替えでは、その項目の`updatedAt`だけを比較する。これにより、別々のサブタスクを複数の団員が同時に完了へ変更する操作は互いに妨げない。

| 現行要素 | 判断 | 理由 |
| --- | --- | --- |
| `goal_sub_tasks`テーブル | 流用 | 共通順序を持つ3種類の親コンテナとして適合 |

| `goalId` | 流用 | 親目標参照として変更不要 |
| `title` | 変更して流用 | 通常項目だけで使用するためnullable化 |
| `isDone` | 流用 | 通常項目の完了状態に使用 |
| `sortOrder` | 流用 | 3種類共通の表示順に使用 |
| `createdAt`、`updatedAt` | 流用 | 表示順の補助と競合検出に使用 |
| 既存行 | 非流用 | 新仕様へ引き継がず削除 |
