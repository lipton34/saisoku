# 編成画像のStorage孤立ファイル点検（Issue #5）

既存の画像アップロード処理は、DB登録に失敗した際にStorage側の補償削除を最大3回試みます。画像削除APIもDB削除後のStorage削除を最大3回試みます。それでもStorageが利用不能な場合、削除に失敗したオブジェクトが残る可能性があるため、本スクリプトで後から調査・回収します。

## 実行方法

本番環境の `DATABASE_URL`、`SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY` を設定した信頼できる実行環境で、まず読み取り専用の確認を実施します。

```bash
npx tsx server/scripts/recoverOrphanBuildImages.ts
```

出力された候補と削除対象が一致することを確認したうえで、必要なら次を実行します。

```bash
npx tsx server/scripts/recoverOrphanBuildImages.ts --apply
```

## 安全策と制限

- `--apply` を付けない場合は削除しません。自動定期削除は現時点では設定していません。
- 公開・非公開の編成画像用バケット以外は調査しません。バケットの公開設定が予期した状態と異なる場合は中断します。
- `posts/{ID}/{ファイル名}` および `drafts/{ID}/{ファイル名}` 形式のJPEG/PNG/WebPのみが対象です。
- Storage側の作成日時が48時間以上前で、投稿画像・下書き画像のDB両方に参照がないものだけ候補にします。削除直前にDB参照を再確認します。
- 一覧取得に失敗した場合は中断します。
- DB変更とStorage操作を完全に原子的にはできません。直前照合と48時間保護によりリスクを抑えていますが、別プロセスから古いStorageパスへの参照が同時に追加される設計が将来導入された場合は対策の見直しが必要です。
- 削除失敗時に自動的に永続キューへ登録する仕組みではありません。定期点検として運用する場合はジョブ実行環境とアラートを別途設定してください。
- 過去の移行時に残した公開画像も、現行DBから未参照かつ規定のパス・経過時間に合致した場合は候補になります。候補の事前確認を必ず行ってください。

今回は本番Storageを操作せず、静的実装・テストで対応しています。
