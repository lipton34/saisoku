# Issue #5：Storage孤立画像の回収手順

本Issueでは、DB登録失敗後の補償削除とStorage削除の一時失敗に対する3回の再試行を実装した。

残存する孤立画像について、読み取り専用の候補一覧を出す運用スクリプト `server/scripts/reconcileBuildImages.ts` を追加した。

## 実行例

```bash
# 既存の正しいDB/Storage環境変数が設定済みの管理用環境で実行
npx tsx server/scripts/reconcileBuildImages.ts
```

デフォルトは**dry-run**。Storage内の `posts/` と `drafts/` を列挙し、投稿・下書きの画像レコードに参照されていない**24時間より古い**画像の候補を表示する。結果にパスが含まれるため報告書やCIログを公開しないこと。

削除には `--delete --confirm-orphan-cleanup` を両方指定する必要がある。**dry-runの一覧を管理者が確認してから手動で実施する。** 本番での実行は今回行っていない。

注意：これは管理者による定期確認方式であり、完全自動の永続キューではない。Storage・DBの接続先を間違えると誤判定が起こり得る。削除直前にDBの参照状態を再確認するが、同時操作との競合を完全に防ぐものではない。安全性を優先し、現状では本番での自動削除を設定しない。

## 残作業

- 隔離Supabase Storage/DBでDB失敗・Storage削除失敗をE2Eで再現する。
- 画像コピーとDB更新の競合時の整合性を別途検証する。
- 孤立画像確認の実運用頻度、担当、通知方法を決める。
- 確認後にDraft PRのマージ・本番反映を判断する。
