# 天井貯金 初期マスター調査

## 1. 状態

調査開始日: 2026-08-05

本書は `docs/32_spark_savings_expansion_feature.md` のUnit 6で予定した、排出時期マスター、獲得イベントマスター、過去実績の初期登録調査である。調査値はユーザー確認前に本番へ登録しない。

## 2. 調査方針

- 公式NEWSを優先する。
- 公式が一覧や合計を提供していない場合は、複数年の開催履歴を整理している攻略情報を補助的に使う。
- 排出日は断定せず、過去3年の実績を包含する広い表示にする。
- 宝晶石換算は、宝晶石 + 単発チケット×300 + 10連チケット×3,000とする。
- 順位、個人貢献度、初回クリア状況で変わる報酬を、全員共通の固定報酬へ混ぜない。

2023～2025年は春枠が3月中旬～4月中旬、夏枠が概ね6月末または7月初旬～8月末に開催されている。

初期登録案は春と夏を分ける。

## 5. 過去実績登録の論点

### 5.1 固定回収と変動報酬

月末シナリオイベントは20箱、全デイリーミッションなどの達成条件を置けば比較的固定値として扱える。一方、古戦場は累計貢献度、個人順位、団順位で宝晶石とチケットが変化する。例えば現行報酬表では累計貢献度だけでも宝晶石や複数の単発チケットが段階的に設定され、スペシャルバトルも順位帯で変わる。

根拠: [GameWith 古戦場報酬一覧](https://xn--bck3aza1a2if6kra4ee0hf.gamewith.jp/article/show/28687)

したがって「平均獲得数」を登録するには、次のいずれかを決める必要がある。

ユーザー確認により、古戦場は開催時点で獲得できる最大数を登録する。累計貢献度報酬、個人順位の最高帯、団順位の最高帯、勝敗など取得条件がある報酬を確認し、重複しない最大値を年別実績へ保存する。証拠メモには最大値の達成条件を明記する。

### 5.2 過去3年月間合計

月間min～maxを出すには、2023～2025年について各月の開催イベント、キャンペーン、配布を同じ基準で記録し、月を集計完了へ設定する必要がある。生放送配布や突発キャンペーンを含むため、イベントマスター作成とは分けて月単位で照合する。

## 6. 初期登録案

ユーザー確認後、最初の投入を次に限定する。

1. 排出時期11件: 水着・浴衣2件、バレンタイン2件、ハロウィン2件、クリスマス2件、ドレスアップ、恒常、不定期・復刻待ち。
2. 獲得イベントマスター17件: monthlyBaseline 5件、scheduled 12件。
3. 過去実績は未確認値を一括投入せず、2025年1月から月単位で根拠を揃えて登録する。
4. 1か月の全項目を照合できた月だけ `isComplete=true` にする。

## 8. 排出時期複数登録の設計

現行の `SparkTarget.availabilityPeriodId` は1件だけを参照するため、季節本来の期間と別月復刻を別々に表示できない。次の中間テーブルへ置き換える。

```text
SparkTargetAvailabilityLink
- id
- targetId
- availabilityPeriodId
- sortOrder
```

- 狙い目1件へ最大2件まで関連付ける。
- 同じ排出時期の重複リンクは禁止する。
- UIは排出時期を複数選択とし、選択済みをチップ表示する。
- APIで0～2件を検証する。
- 現在の本番データは狙い目・排出時期とも0件なので、既存リンク移行は不要である。
- 将来3件以上必要になる可能性に備え、DBは通常の多対多とし、初期UI・APIだけ最大2件へ制限する。

## 9. 狙い目用GBFマスターの調査範囲

2026年8月5日のユーザー確認により、狙い目候補として追加するキャラクター、武器、召喚石の範囲を次で確定した。

### 9.1 キャラクターと武器

- SSRだけを対象にする。
- リミテッド、十二神将、水着、浴衣、バレンタイン、ハロウィン、クリスマス、ドレスアップなど、恒常ではない明確な限定枠を対象にする。
- 恒常キャラクターと恒常武器は登録せず、狙い目の自由入力で対応する。
- キャラクターとキャラ解放武器は別々の `GbfMasterItem` として登録し、調査表では必ず1組で照合する。
- 同じ人物の通常版と限定版、季節違い、属性違いは別レコードにする。
- 水着ゾーイは現在の排出区分を優先してリミテッドだけに分類し、水着・浴衣側へ重複登録しない。
- 表示名は同名版を区別できるように `名称（リミテッド）`、`名称（水着）` のような限定区分を含める。
- コラボ、配布、イベント報酬、ドロップ、交換だけで取得するものは対象外にする。
- 排出終了が公式に確認できるものは削除せず `isActive=false` の候補とし、通常の選択候補へ出さない。

### 9.2 召喚石

- SSRだけを対象にする。
- シリーズ分類が明確で、ガチャから入手する召喚石だけを対象にする。
- マグナ、アーカルム、イベント、ドロップ、交換など、ガチャ以外を主な入手方法とするシリーズは対象外にする。
- シリーズに属さない単発の恒常召喚石は対象外にする。
- 季節限定召喚石は、季節限定であるだけでは採用せず、採用対象シリーズまたは限定召喚石群として一貫して分類できるかを調査してから決める。

### 9.3 登録項目

既存の共通 `GbfMasterItem` を拡張し、狙い目専用マスターは新設しない。各候補について次を調査する。

- 安定した内部ID
- 正式名称
- 表示名
- `kind`: character / weapon / summon
- 属性
- SSR
- 限定区分または召喚石シリーズ
- キャラクターと解放武器の対応
- 検索用の別名
- 排出時期マスターとの対応候補
- 公式NEWSなどの一次出典
- 一覧の完全性を照合した補助出典
- 調査日

画像は登録しない。既存の `thumbnailPath` と `thumbnailUrl` は空にする。

### 9.4 調査と投入の分離

1. 補助一覧から候補集合を作る。
2. 公式のフェス・ガチャ告知で限定区分、正式名称、解放武器を照合する。
3. 同名版、名称変更、排出終了、シリーズ境界を確認する。
4. 種類別件数と未確認件数を集計する。
5. 未確認レコードを有効化せず、ユーザー確認後にseedを実装する。

2026年8月5日時点の補助一覧では、リミテッドキャラクター一覧は71枠まで掲載されている。公式のフェス告知は開催時点の全限定解放武器を列挙するため一次照合に利用できるが、単一記事だけでは現行の全世代を確定できない。複数時点のレジェンドフェス、グランデフェス告知を突き合わせる。

### 9.5 件数と運用負担の見積もり

調査開始時点の概算は次のとおり。季節限定のSSR数と召喚石シリーズ境界を照合する前の幅を持たせた見積もりであり、確定件数ではない。

| 区分 | キャラクター | 武器 | 召喚石 | 合計概算 |
| --- | ---: | ---: | ---: | ---: |
| リミテッド | 約71 | 約71 | - | 約142 |
| 十二神将 | 12 | 12 | - | 24 |
| 季節限定・ドレスアップ等 | 約120～180 | 約120～180 | - | 約240～360 |
| 採用対象のガチャ召喚石シリーズ | - | - | 約30～60 | 約30～60 |
| 全体 | 約203～263 | 約203～263 | 約30～60 | 約436～586 |

数百件はPostgreSQLや検索APIにとって小規模であり、保存・検索のサーバー負荷を理由に削減する必要はない。主な負担は初回の公式照合と、新規限定実装時にキャラクター・解放武器・別名・排出区分を更新する人的運用である。

初期投入は品質を優先し、まずリミテッド、十二神将、現在有効な季節限定、採用対象召喚石シリーズに限定する。過去のSR、排出終了品、コラボ、恒常、シリーズ外召喚石は含めない。この範囲なら全体をおおむね450～600件以内に抑えられる見込みである。

ユーザー確認によりSRは登録せず、SSRだけを段階的に導入する。投入単位は次のとおりとする。

1. 第1段階: リミテッドキャラクターと解放武器、十二神将と解放武器、採用対象のガチャ召喚石シリーズ。
2. 第2段階: 水着・浴衣、バレンタイン、ハロウィン、クリスマスのSSRキャラクターと解放武器。
3. 第3段階: ドレスアップと、調査により限定シリーズであることを確認できたその他のSSRキャラクター・武器。

各段階で候補件数、未確認件数、出典、重複検査を提示し、確認後にその段階だけをseedへ追加する。後続段階の未確認データを同時に有効化しない。

### 9.6 狙い目登録UIの後続拡張

マスターデータ投入後、現在の名前自由入力にマスター検索を追加する。

- 自由入力は残し、恒常や未登録品を引き続き登録できるようにする。
- 種類を選択後、「対象設定」ボタンから前面の選択モーダルを開き、その種類だけをサーバー検索する。
- 種類は対象設定モーダル内で選択し、選択結果を狙い目フォームへ反映する。
- 初期表示で全件を読み込まず、テキスト、属性、区分・シリーズのすべてが未指定の検索はフロントエンドとAPIの両方で拒否する。
- 明示的な検索操作時だけ、検索結果を最大20件取得する。
- キャラクターと武器は属性・限定区分、召喚石は属性・シリーズで追加絞り込みできる。
- 正式名称、表示名、別名、限定区分を検索対象にする。
- 候補には名称、属性、限定区分を表示し、画像は表示しない。
- 候補選択時は `masterItemId` と表示名を設定する。表示名は選択後も本人が修正できる。
- 一致候補がない場合は、そのまま自由入力として保存する。

具体的なAPI、ページング方式、モバイルUIは、初期データ投入完了後の別タスクで確定して実装する。

### 10.2 十二神将

2026年時点の十二神将は12件である。

```text
アニラ、アンチラ、マキラ、ヴァジラ、クビラ、ビカラ、
シャトラ、シンダラ、マコラ、ハイラ、インダラ、サンチラ
```

### 10.5 seedへ落とす際の構造

第1段階の確認済みデータは、既存の `server/data/gbfMasterSeed/` 配下へ種類別に追加する。狙い目専用テーブルや狙い目専用マスターは作らない。

```ts
{
  id: "char-anila",
  kind: GbfMasterKind.character,
  name: "アニラ",
  element: "火",
  rarity: "SSR",
  category: "十二神将",
  tags: ["限定", "十二神将", "レジェンドフェス"],
  metadata: {
    acquisitionGroup: "zodiac",
    unlockWeaponId: "weapon-zodiac-anila",
    availabilityPolicy: "annual-rotation"
  },
  aliases: ["アニラ（十二神将）"]
}
```

キャラクターと解放武器の対応は、文字列名ではなく相手側の安定IDを `metadata.unlockWeaponId` / `metadata.unlockCharacterId` に相互保持する。召喚石は `metadata.series` にシリーズの正規化キーを保持する。

安定IDは既存IDを変更せず再利用し、新規分だけ次の規則で発行する。

- キャラクター: `char-<romanized-name>-grand` または `char-<romanized-name>-zodiac`
- 解放武器: `weapon-grand-<romanized-weapon-name>` または `weapon-zodiac-<romanized-character-name>`
- 召喚石: 既存の `summon-<romanized-name>`

既存seedには、リミテッドや十二神将の一部がすでに登録されている。既存IDを別IDで重複登録せず、名称、カテゴリ、タグ、metadataを補完する。キャラクターと召喚石で同名のものは種類とIDが異なるため別レコードのまま保持する。

現行の `seedGbfMasters()` は `displayName` と `description` を更新対象に含めていない。第1段階では `name` を検索・表示用の正規名称として使い、同名版の識別は括弧付き `name` と別名で行う。将来 `displayName` を使う場合は、型とupsertのcreate/updateを同時に拡張する。

### 10.6 投入前検証

seedへ追加する前に、全候補へ次の機械検査を行う。

- `id` が全種類を通して一意である
- 同一 `kind` 内で正規化後の名称が重複しない
- キャラクターと解放武器の相互IDが存在し、1対1で一致する
- 属性、SSR、限定区分または召喚石シリーズが空でない
- aliasesを正規化した値が同一アイテム内で重複しない
- サムネイルを追加せず、既存画像のない新規レコードは画像項目を空にする
- 未確認候補を `gbfMasterSeedItems` へ含めない

公式サイトは現行リミテッド全件の固定一覧を提供していないため、完全性は現行補助一覧を母集団とし、正式名称・解放武器・追加時期を各実装時の公式フェス告知で照合する。補助一覧側の集計遅延がある場合、推定でフェス区分を埋めない。

### 10.10 狙い目マスター検索

初期マスター投入後の後続作業として、狙い目登録モーダルへマスター検索を実装した。

- 種類を選択してから、同じ種類の有効なマスターだけを検索する
- 名前、表示名、別名、限定区分、タグを検索対象にする
- テキストまたは絞り込み条件を指定した明示検索時だけ、最大20件をサーバーから取得する
- キャラクター・武器は属性と限定区分、召喚石は属性とシリーズで絞り込める
- 候補選択時に `masterItemId` と名前を設定するが、名前は引き続き編集可能
- 候補がない恒常・未登録品は自由入力で保存できる
