# 天井貯金拡張機能仕様

最終更新: 2026-08-05

## 1. 文書の目的と状態

本書は、実装済みの「天井貯金」へ、本人専用の狙い目リスト、共有の排出時期、共有の獲得目安、本人が任意で有効化する獲得・使用履歴を追加する拡張仕様である。

基本の天井回数、所持数、追加で必要な宝晶石、認証、所有権、既存ルートは `docs/31_spark_savings_feature.md` を基礎とする。本書と同文書が異なる場合、拡張対象については本書を後続正本として優先する。

本仕様は確定済み・未実装である。排出時期マスターと獲得イベントマスターの具体的な初期値は未調査であり、本書の確定だけでは有効化しない。実装、本番migration、初期データ調査、seed、本番デプロイはそれぞれ別作業として扱う。

## 2. 目的

- 狙っているキャラクター、召喚石、武器と必要数を本人だけが管理できるようにする。
- 例年の大まかな排出時期を、日単位の確定予定と誤認させず確認できるようにする。
- 当月の開催予定に応じた獲得目安と、来月・再来月の例年月間実績を確認できるようにする。
- 履歴を利用したい本人だけが、獲得、使用、残高調整と月別差分を記録できるようにする。
- 現在の「何連分あるか」を最上部で確認できる基本UXを維持する。

## 3. 公開範囲

本人専用:

- 天井貯金の現在残高
- 狙い目と、その現在数・希望数
- 狙い目と目標・編成のリンク
- 履歴の有効状態、集計開始月、全履歴

団内共有:

- 排出時期マスター
- 獲得イベントマスター
- 過去の獲得実績
- 天井貯金専用の手動開催予定
- 月別集計完了状態

本人専用データは、他ユーザーへ件数、ID、リンク先を含めて存在自体を返さない。共有データは認証済み団員全員が取得、作成、編集、削除できる。

## 4. 対象外

- 排出時期の正確な日付予測
- ガチャ開催情報の自動取得と自動確定
- 既存 `EventOccurrence` と天井貯金専用開催予定の共有
- 継続的なスクレイピング
- 獲得目安による天井到達予定日の計算
- 本人の履歴を共有獲得目安へ自動利用すること
- 履歴開始前と未入力期間の増減推測
- 過去日・未来日を指定した履歴入力
- 個別履歴の直接編集・削除
- 編成・目標側から本人専用の狙い目を表示する逆リンク
- 数量目標・進捗管理への直接リンク
- 持ち物チェッカーとの連携

持ち物チェッカーは未実装であり、本機能では連携しない。狙い目の任意 `masterItemId` を将来の照合候補として保持し、具体的な連携と値の優先順位は持ち物チェッカー実装時に決める。

## 5. 既存天井貯金の変更

`SparkSavings` は所持数と履歴設定だけへ簡略化する。

維持:

- `ownerId`
- `crystalCount`
- `singleTicketCount`
- `tenPullTicketCount`
- `createdAt`
- `updatedAt`

追加:

- `historyStartedAt`: 履歴開始日時。nullなら履歴無効
- `historySummaryStartMonth`: 集計開始月

削除:

- `targetName`
- `plannedAt`
- `memo`

既存の目的、使用予定日、メモは移行せず削除してよい。既存の宝晶石とチケットの現在値は維持する。削除対象カラムの非null件数をmigration適用前に確認する。

## 6. 画面構成

`/spark-savings` の最上部には、すべてのタブで共通して現在の合計回数と追加で必要な宝晶石を表示する。

```text
現在 204連分

追加で必要な宝晶石
28,701個（あと96連）
```

その下を4タブに分ける。

```text
貯金｜狙い目｜獲得目安｜履歴
```

タブはクエリで保持する。

```text
/spark-savings?tab=savings
/spark-savings?tab=targets
/spark-savings?tab=rewards
/spark-savings?tab=history
```

不正または未指定のタブは `savings` とする。タブ切り替えでは、既に読み込んだ現在残高を不要に再取得しない。

## 7. 貯金タブ

表示:

- 宝晶石数と、その宝晶石による回数
- 単発チケット数
- 10連チケット数
- 編集
- リセット

例:

```text
宝晶石
55,299個（184連分）

単発チケット
0枚

10連チケット
2枚
```

チケットによる合計回数は内部計算へ使用するが、独立項目として表示しない。宝晶石分とチケット分を統合した回数は画面最上部の「現在○連分」で表示する。

編集項目は宝晶石、単発チケット、10連チケットの3項目だけとし、操作名は「編集」を維持する。

履歴無効時の編集とリセットは履歴を作らない。履歴有効時の編集とリセットは、現在残高の更新と残高調整履歴の作成を同じDBトランザクションで行う。

## 8. 狙い目

### 8.1 データ

`SparkTarget` は次を持つ。

- `id`
- `ownerId`
- `itemType`: `character`、`summon`、`weapon`
- `name`
- 任意の `masterItemId`
- `desiredCount`: 希望数
- `ownedCount`: 現在数
- 任意の `availabilityPeriodId`
- 任意の `note`
- `sortOrder`
- `createdAt`
- `updatedAt`

入力上限:

| 項目 | 上限 |
| --- | ---: |
| 名前 | trim後100文字 |
| 希望数 | 1～999 |
| 現在数 | 0～999 |
| メモ | trim後500文字 |

名前は自由入力を許可する。GBFマスターから候補を選択した場合だけ `masterItemId` を保存し、狙い目の表示名は本人が変更可能とする。GBFマスター本体は変更しない。画像は表示しない。

`masterItemId` の参照先はキャラクター、召喚石、武器だけを許可する。マスター削除時はSetNullとし、狙い目を残す。

### 8.2 表示条件

通常一覧へ表示する条件:

```text
ownedCount < desiredCount
```

達成条件:

```text
ownedCount >= desiredCount
```

達成済みデータは削除せず、通常一覧から隠す。「達成済みも表示」をONにした場合だけ一覧末尾へ表示する。現在数を希望数未満へ戻すと通常一覧へ自動的に戻る。

優先度と手動の取得状態は持たない。狙い中の表示順は本人が手動で並べ替える。

### 8.3 カード

```text
水着キャラクターA
キャラクター　現在0 / 希望1

例年の排出目安
6月下旬～8月中

関連：目標2件・編成1件
```

カード詳細では、種別、名前、現在数、希望数、排出時期、メモ、関連目標、関連編成、編集、削除を表示する。

### 8.4 画面とルート

```text
/spark-savings/targets/new
/spark-savings/targets/:targetId/edit
```

作成・編集は入力項目が多いため専用画面とする。狙い目タブを表示している場合だけ、下部ナビゲーションと重ならない右下へ作成ボタンを表示する。

### 8.5 目標リンク

`SparkTargetGoalLink` で狙い目1件へ複数の通常目標を関連付けられる。

選択可能:

- 本人の個人目標
- 本人が閲覧可能な団内目標

選択不可:

- 他ユーザーの個人目標
- 数量目標・進捗管理への直接リンク

目標削除時はリンクだけをCascade削除する。目標APIと目標画面から狙い目への逆リンクは返さない。リンク作成・更新時と取得時の両方で、現在の目標閲覧権限を検証する。

### 8.6 編成リンク

`SparkTargetBuildLink` で狙い目1件へ複数の団内公開編成を関連付けられる。他ユーザーの団内公開編成も選択可能とし、編成下書きは対象外とする。

編成削除時はリンクだけをCascade削除する。編成APIと編成画面から狙い目への逆リンクは返さない。関連編成は取得時にも団内公開状態を検証する。

## 9. 排出時期マスター

`SparkAvailabilityPeriod` は団内共有で、狙い目1件につき最大1件を関連付ける。

保存項目:

- `name`
- `displayLabel`
- `scheduleType`: `annual`、`permanent`、`irregular`
- annualの場合の開始月・開始区分
- annualの場合の終了月・終了区分
- `sortOrder`
- `isActive`
- `createdById`
- `updatedById`
- `createdAt`
- `updatedAt`

月内区分:

- `early`: 上旬
- `middle`: 中旬
- `late`: 下旬

利用者向けには日単位の予定を表示せず、`displayLabel` の「3月中」「6月下旬～8月中」「不定期」「常設」などを表示する。

### 9.1 調査条件

初期マスターは推測で作成・有効化しない。実装とは別に、季節限定区分、過去の排出開始・終了時期、年ごとの変動幅、周年・十二神将・季節限定・常設・不定期の扱いを調査する。

公式情報を優先し、必要な場合だけ信頼できる参照先を補助的に使用する。記事、表、画像は転載せず、確認した時期を広めな表示へ再構成する。調査結果と根拠をユーザーが確認した後に初期マスターを有効化する。

### 9.2 削除

使用中のマスターは物理削除せず無効化する。未使用マスターだけ確認後に削除可能とする。狙い目の外部キーはSetNullとしてデータ損失を防ぐ。

## 10. 獲得イベントマスター

`SparkRewardEventType` は団内共有で、過去実績と手動開催予定の分類に使用する。

保存項目:

- `eventKey`
- `name`
- `aggregationMode`: `scheduled` または `monthlyBaseline`
- 任意の `description`
- `sortOrder`
- `isActive`
- 作成者・最終編集者・日時

`scheduled` は当月開始の手動開催予定がある場合だけ、当月内訳へ表示する。`monthlyBaseline` はログイン・キャンペーンなど開催予定なしで毎月表示する基礎分に使用する。

正式なイベント種類と分類は後日の調査で確定し、未確認の初期マスターを有効化しない。

## 11. 過去の獲得実績

`SparkRewardRecord` は団内共有で次を持つ。

- `rewardEventTypeId`
- 対象年・対象月
- `occurrenceName`
- 任意の開始日
- `crystalCount`
- `singleTicketCount`
- `tenPullTicketCount`
- `isIncludedInEstimate`
- 任意の根拠メモ
- 任意の参考URL
- 作成者・最終編集者・日時

数値は0以上の整数とし、天井貯金の現在値と同じ上限を適用する。少なくとも1種類が1以上でなければ保存しない。参考URLは有効なHTTP(S) URL、最大2,048文字とする。

宝晶石換算:

```text
crystalEquivalent
  = crystalCount
  + singleTicketCount * 300
  + tenPullTicketCount * 3000
```

各開催実績を換算してから、対象サンプルの最小値と最大値を取得する。宝晶石とチケットを別々に最小・最大化してから合算しない。

同一イベントマスター、対象年月、開催名が一致する場合は重複候補として保存前に警告するが、同月の複数開催を許可するためDBの一意制約にはしない。

## 12. 月別集計完了状態

`SparkRewardMonthStatus` は `year + month` をuniqueとし、各過去年月が月間合計へ利用できる状態かを保存する。

- `year`
- `month`
- `isComplete`
- 最終編集者
- `updatedAt`

月間合計へ使用する条件:

- 対象年月が集計完了
- 実績が集計対象
- 表示対象年より前の3年間に含まれる

実績が一部しかない集計未完了月を月間合計へ使用しない。3年分すべてが揃っていなくても、完了した1～2年分があれば暫定表示できる。画面にはサンプル年数を表示しない。

## 13. 手動開催予定

`SparkRewardSchedule` は天井貯金専用の団内共有データとし、既存 `EventOccurrence` を参照・同期しない。

保存項目:

- `rewardEventTypeId`
- `name`
- `startOn`
- 任意の `endOn`
- 任意のメモ
- 作成者・最終編集者・日時

すべて手動登録し、保存済み予定は確定情報として扱う。暫定・候補状態は初期実装に含めない。月別判定には開始日の日本時間年月だけを使用し、終了日が翌月でも翌月へ計上しない。開始日が前月の予定も当月へ計上しない。

自動スクレイピングは行わない。将来公式NEWSを利用する場合も、自動確定ではなく利用者確認前の候補作成までとし、候補は集計へ含めない。この候補取り込みは本仕様の対象外とする。

## 14. 獲得目安タブ

### 14.1 当月

当月は次をイベント別に表示する。

- 当月開始の手動開催予定に紐づく `scheduled`
- 当月の `monthlyBaseline`

```text
8月の獲得目安

月末イベント
1,500～2,100個相当

四象降臨
2,500～3,400個相当

ログイン・キャンペーン
3,000～4,500個相当
```

イベント別範囲は、表示年より前の3年間に登録された同一イベントマスターの集計対象実績から求める。同一年に複数開催がある場合はすべてをサンプルにする。

### 14.2 来月・再来月

来月・再来月は、表示対象と同じ暦月における過去3年の完了済み月間合計から、最小～最大を表示する。開催予定がなくても例年実績を表示できる。

```text
9月
例年実績 18,000～26,000個相当
開催予定：古戦場

10月
例年実績 15,500～22,000個相当
```

表示値は将来予測ではなく、過去3年の実績範囲である。天井到達予定日や将来残高は計算しない。

### 14.3 空状態

- 当月予定なし
- イベント別実績なし
- 完了済み月間実績なし
- マスター未登録
- 共有データ取得エラー

を区別する。データがない場合は0として表示せず「実績未登録」とする。

## 15. 履歴

### 15.1 任意有効化

履歴は本人が「履歴を使い始める」を実行するまで無効とする。有効化時にサーバーの日本時間で `historyStartedAt` を保存し、その時点の残高を `start` 履歴として保存する。

`start` は月別の獲得、使用、調整へ含めず、startだけの月は月別カードを表示しない。

### 15.2 履歴種別

`SparkHistoryEntry` は次の種別を持つ。

- `start`
- `earn`
- `spend`
- `adjustment`

保存項目:

- `ownerId`
- `entryType`
- サーバーが決定する日本時間の操作日
- 宝晶石の符号付き増減
- 単発チケットの符号付き増減
- 10連チケットの符号付き増減
- 操作後の各残高
- 入手元・用途・調整理由となるタイトル
- 任意の補足メモ
- `createdAt`

履歴入力で日付を選択させない。ブラウザから操作日を受け取らず、サーバーが `Asia/Tokyo` の当日を保存する。過去日・未来日の履歴入力は扱わない。

タイトルはtrim後1～100文字、補足メモはtrim後500文字とする。

### 15.3 獲得

本人は宝晶石、単発チケット、10連チケット、入手元、任意メモを入力する。3種類すべて0の場合は拒否する。履歴作成と現在残高への加算を同じDBトランザクションで行う。

### 15.4 使用

本人は使用した宝晶石、単発チケット、10連チケット、用途、任意メモを正の数で入力する。サーバーで負の差分へ変換し、現在残高を超える使用を拒否する。履歴作成と残高減算を同じDBトランザクションで行う。

### 15.5 残高調整

本人はゲーム内の実際の所持数3種類と調整理由、任意メモを入力する。サーバーが変更前後の差分を計算し、履歴作成と残高更新を同じDBトランザクションで行う。3種類すべて現在値と同じ場合は履歴を作成しない。

### 15.6 通常編集とリセット

履歴無効時は現在残高だけを更新する。履歴有効時は、通常編集とリセットも `adjustment` として自動記録し、現在残高と履歴を同じトランザクションで更新する。

リセットでは現在残高をすべて0にする。履歴有効時は「リセット」を調整理由として差分を記録する。過去履歴と履歴有効状態は維持する。

### 15.7 修正と全削除

個別履歴の編集・削除は行わない。誤入力は残高調整で訂正する。

「履歴をすべて削除」は本人だけが実行できる独立した危険操作とする。確認後、全履歴を削除し、`historyStartedAt` と `historySummaryStartMonth` をnullへ戻す。現在残高は変更しない。操作は元に戻せない。

## 16. 履歴集計

### 16.1 月別

`earn`、`spend`、`adjustment` が1件以上存在する月だけ表示・集計する。入力がない月と `start` しかない月は表示しない。

```text
2026年8月

獲得  +14,400個相当
使用   -9,000個相当
調整     +500個相当
差分   +5,900個相当
```

換算式は共有実績と同じとする。獲得、使用、調整を分け、差分は3種類の合計とする。月別カードを展開すると同月の個別履歴を新しい順に表示する。

### 16.2 集計開始月

履歴開始月を既定の `historySummaryStartMonth` とする。本人は履歴開始月から現在月までの任意の年月へ変更できる。入力がない月も選択可能とし、履歴開始前と未来月は拒否する。

表示は日付ではなく年月とする。

```text
集計開始月：2026年8月

2026年8月から現在
獲得  +42,300個相当
使用  -18,000個相当
調整     +500個相当
差分  +24,800個相当
```

集計開始月の変更は履歴と現在残高を変更せず、設定だけを保存する。

## 17. 履歴タブ

履歴無効時は説明と「履歴を使い始める」を表示する。有効時は次を表示する。

1. 獲得、使用、残高調整
2. 集計開始月
3. 集計開始月から現在までの合計
4. 入力がある月だけの月別カード
5. 履歴の操作メニュー

獲得、使用、残高調整は繰り返し操作を優先し、内部スクロール可能なダイアログで入力する。保存中は二重送信を防ぎ、失敗時は入力を保持する。

## 18. 共有データ編集画面

```text
/spark-savings/reference-data
```

タブ:

1. 排出時期
2. 獲得イベント
3. 過去実績
4. 開催予定
5. 月別集計状態

通常の天井貯金画面では共有データの閲覧結果だけを表示し、編集入口は目立たない「データ管理」メニューへ置く。

共有データの更新では編集開始時の `updatedAt` を `expectedUpdatedAt` として送り、不一致なら409を返して自動上書きしない。

## 19. 共有データ監査

共有データは作成者と最終編集者を保存する。さらに内部監査ログへ次を保存する。

- 対象種別
- 対象ID
- 操作: create、update、delete
- 操作者ID
- 操作者名のスナップショット
- 変更前後の主要値
- 操作日時

監査ログは通常の利用者画面へ表示しない。削除操作も、削除前の名称と主要値を残す。通常APIから監査ログを変更・削除できないようにする。

## 20. 削除ルール

- 狙い目: 本人だけが確認後に削除可能。関連リンクをCascade削除する。
- 使用中の排出時期: 物理削除不可。無効化または関連解除を行う。
- 実績・予定を持つ獲得イベントマスター: 物理削除不可。無効化を使用する。
- 未使用の共有マスター: 全団員が確認後に削除可能。
- 過去実績・開催予定: 全団員が確認後に削除可能。
- 月別集計状態: 全団員が完了解除可能。
- 履歴: 個別削除不可。本人だけが全削除可能。

共有マスターの削除で実績、予定、狙い目を巻き込むCascade削除は行わない。

## 22. エラー

- 入力不正: 400
- 未認証: 401
- 本人専用データが存在しない、または閲覧不能: 詳細を漏らさない404
- 共有データの更新競合: 409
- 使用中マスターの削除拒否: 409
- 現在残高を超える使用: 400
- 履歴未有効時の履歴操作: 409
- 予期しないサーバーエラー: 500

エラーは既存形式の日本語 `message` を返す。保存失敗時は画面入力を維持する。

## 23. モバイル・アクセシビリティ

- 最小幅320pxを維持し、360px、768px、1280px以上で同じ情報と操作を提供する。
- 360pxで4タブを1行表示し、収まらない場合もページ全体ではなくタブ領域内だけをスクロール可能にする。
- 最上部の現在回数と追加必要宝晶石を、どのタブでも最初に確認できるようにする。
- 狙い目の長い名称、排出時期、メモ、関連名を折り返す。
- 大きな数値がカードを押し広げないようにする。
- 主要操作は可能な範囲で約44px以上とする。
- 達成、集計完了、履歴種別を色だけで表現しない。
- ダイアログはviewport内へ収め、本文を内部スクロール可能にする。
- 下部ナビゲーションと固定作成ボタンが内容を隠さないようにする。
- すべての入力へlabelを関連付け、アイコンだけの操作へ `aria-label` と `title` を付ける。

## 24. migration

- 新しいモデル、外部キー、unique、CHECK、インデックスを新規migrationで追加する。
- 既存migrationを編集しない。
- `SparkSavings.targetName`、`plannedAt`、`memo` を削除する。
- 既存の宝晶石とチケットは変更しない。
- 削除カラムの非null件数と `SparkSavings` 件数を確認する `preflight.sql` を追加する。
- 初期マスターと過去実績をmigrationへ含めない。
- 調査済み初期データは、ユーザー確認後にseedまたは共有データ管理画面から登録する。
- 本番migration、seed、デプロイはローカル実装・検証と分離し、実行直前に対象環境と適用順を再確認する。

## 25. テスト

本人専用データ:

- 狙い目、リンク、履歴を他ユーザーへ返さない。
- 他ユーザーIDを入力として受け取らない。
- 個人目標、団内目標、非公開編成、公開編成のリンク可否。
- 狙い目の希望数・現在数境界と達成表示。
- 並び替えと達成済み表示切り替え。

履歴:

- 履歴開始時の残高スナップショット。
- サーバーの日本時間による操作日。
- 獲得、使用、残高調整と現在残高のトランザクション整合。
- 残高超過使用の拒否。
- 履歴有効・無効時の通常編集とリセット。
- startだけの月を月別表示しない。
- 入力がある月だけの月別集計。
- 集計開始月の最小・最大境界。
- 全履歴削除後も現在残高を維持すること。

共有データ:

- 全認証利用者の作成・編集・削除。
- `expectedUpdatedAt` の競合409。
- 使用中マスターの削除拒否。
- 作成者、最終編集者、監査ログ。
- 月をまたぐ予定を開始月だけへ計上。
- 各実績を換算してからmin・maxを求めること。
- 集計未完了月を月間範囲から除外すること。
- 1～3年分の完了データによる月間範囲。
- 重複候補警告と同月複数開催の許可。

画面:

- 4タブとクエリ復元。
- 未登録、空状態、読み込み、成功、エラー、競合、削除確認。
- 360px、768px、1280px以上。
- 長文、最大値、最大件数、下部ナビゲーションとの重なり。

最低限のコマンド:

```text
npm run prisma:generate
npm run typecheck
npm test
npm run build
git diff --check
```
